# Git and quality checks

This application has its own Git repository on branch `main`. Creation does not
stage files, make a commit, configure a remote, install hooks or download tools.
Run the following from **this application's directory**, using Python 3.8+:

```sh
python -m venv .venv
# Linux/macOS: source .venv/bin/activate
# Windows PowerShell: .venv\Scripts\Activate.ps1
python -m pip install -r tools/quality/requirements.txt
python -m pre_commit install
git add .
python -m pre_commit run --all-files
```

Hooks download their pinned external tools on first use. Mosaico checks execute
`mosaico-tools/tools/quality/check_project.py` from the workspace's utils checkout;
no generic checker implementation is copied into this application. Keep that
checkout available at the relative path rendered in `.pre-commit-config.yaml`.
Its revision is managed with the workspace's utils dependency, just like the
build tooling. Pin that dependency to a reviewed revision in local development
and CI; updating it updates the shared checks. Copying this application alone
requires restoring the dependency and adjusting its four hook entries if the
workspace layout changes. Formatting hooks may change
files and fail that invocation: review the changes, stage them again, and rerun.
`--all-files` checks tracked/staged files, so `git add .` is necessary before the
first run. Subsequent commits check staged changes. Each clone needs its own
`pre_commit install`. No user identity or remote is set by the project creator.
Git 2.28+ is required to create an application.

AStyle rules (`astyle.yml`), Ruff rules (`ruff.toml`) and project policy live in
this directory. The root `.pre-commit-config.yaml` points at them explicitly.
For standalone Python checks, pass `--config tools/quality/ruff.toml` to Ruff;
configure the editor's Ruff integration with the same path if needed. Git and
EditorConfig files stay at the root so their normal discovery still works.

If creation reported preserved configuration files, those files take precedence
over the defaults described here. Review the existing hook configuration and
enable commands, especially if it references its own tools or rules. With default
hooks, a template-owned `tools/quality/astyle.yml` or `ruff.toml` is used directly.
Otherwise an existing root `.astyle-rules.yml` is used for AStyle, and a root
`.ruff.toml`, `ruff.toml` or `pyproject.toml` keeps Ruff's native configuration
discovery (including nested overrides). Ruff defaults apply where such a
pyproject has no Ruff settings. Unused default format files are not added.
Template-owned hook configurations are always kept unchanged.

## Default checks

- Text: trailing spaces, final newline and LF endings. Markdown's two-space
  line break is preserved. Binary assets are not passed to text formatters.
- C/C++: ESP-IDF 6.2 AStyle defaults, using `astyle_py` 1.0.5 / AStyle 3.4.7.
  Python: Ruff checks and formatting, targeting Python 3.8.
- Configuration: YAML, JSON and TOML syntax.
- Secrets: private-key detection and detect-secrets. There is no automatically
  accepted secrets baseline. Review false positives individually; use documented
  detect-secrets inline allowlisting only for known non-secret values.
- Commits: conflict markers, files above 5 MiB, forced additions of build
  outputs, downloaded components, caches and local credential files.
- Files: case collisions, broken symlinks, and executable/shebang consistency.
  On Windows use `git update-index --chmod=+x SCRIPT` for executable scripts.
- Components: project-owned `components/*` use IDF Component Manager names
  (2-64 ASCII letters/digits, single underscore or hyphen separators) and a
  tracked `CMakeLists.txt`. `idf_component.yml` is optional. No `esp_` prefix
  is required. This is a naming/discovery check, not an IDF configure substitute.

Source formatters and static analysis exclude third-party and generated trees.
Artifact checks have no such exclusion, so `git add -f build/...` is still
rejected. Source fonts, images, audio and `.bin` resources remain allowed; the
5 MiB size limit can be adjusted in `.pre-commit-config.yaml` for reviewed assets.
`sdkconfig*.defaults` and component manifests stay versioned. The application
root's `dependencies.lock` is ignored by default and regenerated by IDF Component
Manager. Fresh resolution can change indirect dependency versions even when
direct dependencies are pinned. Release projects should explicitly choose a
portable lock-file or equivalent complete dependency pinning strategy. Do not
edit generated lock files by hand.

## Manual C/C++ analysis

First build the application with the consuming workspace's `mosaico.py` launcher
and its configured ESP-IDF toolchain. Then, from this application's directory:

```sh
python -m pre_commit run mosaico-cppcheck --hook-stage manual --all-files
```

The hook installs the pinned `cppcheck` wheel 1.5.1 and imports `build/compile_commands.json`.
This manual stage uses exhaustive analysis to avoid the normal branch-analysis
limit on SDK-heavy translation units; it can take longer than commit checks.
Set `compile_commands` in `tools/quality/policy.json` if the build lives elsewhere
(including an Iris wrapper build). Alternatively, set arguments on the
`mosaico-cppcheck` hook in `.pre-commit-config.yaml`:

```yaml
args: [--compile-commands, /path/to/compile_commands.json]
```

Only this application's C/C++ translation units are selected. Missing tools,
missing databases, and databases with no application sources are errors. Analysis
failures return a nonzero status. This check neither builds nor flashes a device.
Cppcheck is not the ESP-IDF compiler: GCC-specific constructs can produce analyzer
diagnostics even after a successful firmware build. Parsing failures remain visible and fail the manual check; they are not silently
treated as an analyzed, passing source file.

## Project-specific rules

`tools/quality/policy.json` provides two opt-in lists and an optional prefix:

- `application_component_prefix`: empty/omitted accepts ordinary ESP-IDF names.
  Built-in application templates set `app_` for their application-only `components/`
  tree; keep third-party components under their documented dependency locations.
  This checks naming, not dependency cycles or API contracts.

- `forbidden_apis`: C identifiers such as `gets`. The check matches calls and
  declarations outside ordinary comments/string literals in project-owned C/C++
  files. It is a lexical guard, not a full preprocessor or C++ parser. Defaults
  are empty; ESP-IDF APIs are not prohibited indiscriminately.
- `generated_checks`: lists of command arguments for the project's existing
  **check-only** generators. Each command runs from the application root without
  a shell and must return nonzero when tracked generated sources are stale.
  `{python}` resolves to the check's Python interpreter. No commands are run
  during project creation. Defaults are empty because the built-in UI bundles
  are build outputs, not versioned generated source.

For example, once the project implements the corresponding check-only script:

```json
{
  "forbidden_apis": ["gets"],
  "generated_checks": [["{python}", "tools/generate_assets.py", "--check"]],
  "compile_commands": "build/compile_commands.json"
}
```

Run configured synchronization checks with:

```sh
python -m pre_commit run mosaico-generated --hook-stage manual --all-files
```

Project policy and external hook pins belong to this application. Put project-only
checkers beside the corresponding generator and refer to them in `generated_checks`;
shared rules belong in the utils checker. Review both configuration and the utils
revision before enabling hooks. See the [pre-commit documentation](https://pre-commit.com/)
for hook installation and configuration.
