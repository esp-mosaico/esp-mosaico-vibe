# DFS 与显示传输

用于适配频率下限、排查低频显示异常或 PM 锁阻止降频。先检查所用 IDF 和驱动源码；本例来自 ESP32-S31、IDF 6.2 开发版本的 Vibe，不能直接作为其他芯片的时钟表或 API 合约。

## 什么决定实际频率

1. `esp_pm_configure()` 配置允许范围，不保证 CPU 始终运行在下限。
2. 在本例的非 SMP 配置中，可运行任务使 RTOS 要求 CPU_MAX；没有可运行任务且锁允许时，才有低频窗口。
3. S31 配置最高 320 MHz 时，CPU_MAX 锁要求 320 MHz；仅 APB_MAX 锁时官方表列出 CPU/APB 为 53.3 MHz；没有这些锁才允许配置的下限，例如 40 MHz。
4. 显示、输入、后台采样和网络活动可使系统离开低频。产品“15 秒空闲后停动画”与上述自动调频不是同一个状态机。

因此任务中调用 `esp_clk_cpu_freq()` 常读到 320 MHz，不能证明低频无效；方括号显示 `[40–320]` 只证明配置范围。使用目标 SDK 支持的 PM 锁/驻留统计确认真实进入低频，并查看稳定测量窗口的模式占比。

## APB 锁为何可能还不够

SPI 驱动使用的 APB 锁用于约束其总线时钟，不承诺 CPU、内存访问带宽和应用层显示时序都保持最高性能。帧缓冲在 PSRAM、采用 XIP、异步 DMA 或多段提交时，需要核对整个数据路径。CPU 为 40 MHz 不代表外部 PSRAM 也为 40 MHz。

Vibe 之前有低频花屏、闪烁和 MSPI/PSRAM abort 记录，但未严格定位到单一根因。后续应用级 CPU_MAX 保护在 40 MHz 下获得了正常显示与交互反馈；这不能反推“所有 SPI 都必须加 CPU_MAX”或“已证明是 APB 锁的 bug”。

## 需要应用层保护时的生命周期

以下是逻辑顺序，不是 BSP API 名称：

```text
初始化 PM 锁及显示同步对象，之后再启用应用 DFS

串行进入显示操作
    获取/沿用 CPU_MAX 约束
    执行显示命令、绘制和提交
    等待该保护范围内所有 DMA/fence/传输尾部完成
    成功：释放约束
    失败：保留约束，报告错误，等后续确认排空后再释放
串行退出显示操作
```

保持锁计数平衡，覆盖获取失败、部分提交失败、排空超时及后续恢复。由既有显示锁/单一所有者串行化相关操作；亮度、旋转命令与画面传输可能共用 SPI，也需纳入检查。

不能只等第一个分块完成，不能把队列已提交当 DMA 完成，不能与尚在访问帧缓冲的传输并发修改资源。使用组件真实提供的 API，不虚构通用 `quiesce()` 接口。若驱动本身已满足完整需求，避免再重复加锁。

Vibe 本轮选择每帧排空以缩小实验变量，但可能牺牲流水线并行；其他 App 应按驱动能力用 fence/完成事件保留吞吐，不机械复制阻塞等待。

## 检查顺序

- 不降频：查可运行任务、周期唤醒和 PM 锁持有时间，确认显示锁没有长期泄漏。
- 进入低频后异常：先回到已验证的频率范围，留存日志；核对 PSRAM/XIP、驱动时钟源、事务生命周期与并发访问。
- TE 超窗：检查实际传输时长与面板刷新窗口。增加 CPU_MAX 不会自动扩大 SPI 带宽或证明没有撕裂。
- USB/网络超时：记录可重复性及故障时的任务/PM 状态；握手或重连成功不能替代功能验收。
